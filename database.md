# Database Design

## 1. Purpose

This document defines the current database structure and relationships for the application.

The database covers 3 main domains:

1. **User Profile & Requirements**
2. **User Activity & Events**
3. **Training Plan**

This document is the **source of truth for database implementation**.

> Important: Do not create additional tables, fields, relationships, enums, or business rules unless explicitly specified in requirements.

---

# 2. Database Conventions

## Naming

Use:

* `snake_case` for table names and column names
* plural nouns for main entity tables where already defined
* `id` as primary key unless the current schema explicitly uses another primary key
* `<entity>_id` for foreign keys

Example:

```text
users
events
training_plans

user_id
event_id
```

---

## Timestamps

Most tables contain:

```text
created_at
updated_at
```

Recommended application behavior:

* `created_at` is set when the record is created
* `updated_at` is updated whenever the record changes

Do not use these fields for business events if a dedicated timestamp already exists.

Examples:

```text
joined_at
verified_at
rejected_at
recorded_at
scheduled_at
```

# 4. User Profile & Requirements

## 4.1 users

Primary account table.

Stores authentication and account-level information.

### Fields

| Field           | Type         | Description                       |
| --------------- | ------------ | --------------------------------- |
| `id`            | int PK       | Unique user ID                    |
| `username`      | varchar(100) | Username                          |
| `email`         | varchar(255) | User email                        |
| `password_hash` | varchar(255) | Hashed password                   |
| `tier`          | varchar(20)  | Account tier: `free` or `premium` |
| `created_at`    | timestamp    | Record creation time              |
| `updated_at`    | timestamp    | Last update time                  |

### Notes

Never store plain-text passwords.

`password_hash` must contain only the hashed password generated by the authentication layer.

---

## 4.2 user_demographics

Stores basic demographic information for a user.

### Relationship

```text
users 1 — 1 user_demographics
```

`user_demographics.user_id` is both:

* Primary Key
* Reference to `users.id`

### Fields

| Field        | Type        | Description          |
| ------------ | ----------- | -------------------- |
| `user_id`    | int PK      | User ID              |
| `age`        | int         | User age             |
| `gender`     | varchar(20) | User gender          |
| `created_at` | timestamp   | Record creation time |
| `updated_at` | timestamp   | Last update time     |

A user can have a maximum of one demographic record.

---

## 4.3 user_constraints

Stores constraints affecting the user's workout availability or activity requirements.

### Relationship

```text
users 1 — N user_constraints
```

A user may have multiple constraints.

### Fields

| Field              | Type         | Description                                |
| ------------------ | ------------ | ------------------------------------------ |
| `id`               | int PK       | Constraint ID                              |
| `user_id`          | int FK       | Owner of the constraint                    |
| `constraint_type`  | varchar(30)  | Type of constraint                         |
| `area_type`        | varchar(30)  | Type of area/location                      |
| `area_label`       | varchar(100) | Human-readable area                        |
| `day_of_week`      | varchar(20)  | Available day                              |
| `available_from`   | time         | Start of availability                      |
| `available_to`     | time         | End of availability                        |
| `weekly_frequency` | int          | Desired/available frequency per week       |
| `note`             | text         | Additional note                            |
| `is_active`        | boolean      | Whether the constraint is currently active |
| `created_at`       | timestamp    | Record creation time                       |
| `updated_at`       | timestamp    | Last update time                           |

### Usage

This table can represent multiple user requirements independently.

Do not overwrite an existing constraint when another constraint is added.

Create another row instead.

# 5. User Activity

## 5.1 user_history_level

Stores historical snapshots of a user's fitness level and running performance.

### Relationship

```text
users 1 — N user_history_level
```

This table represents **history**, not only the latest state.

Never overwrite previous records when recording a new fitness assessment.

Create a new record.

### Fields

| Field                  | Type         | Description                         |
| ---------------------- | ------------ | ----------------------------------- |
| `id`                   | int PK       | History ID                          |
| `user_id`              | int FK       | User                                |
| `fitness_level`        | varchar(20)  | Fitness level at that point in time |
| `running_distance`     | decimal(6,2) | Running distance                    |
| `running_duration_min` | int          | Running duration in minutes         |
| `recorded_at`          | timestamp    | When the fitness data was recorded  |
| `created_at`           | timestamp    | Record creation time                |
| `updated_at`           | timestamp    | Last update time                    |

When retrieving the latest fitness level, order by:

```sql
recorded_at DESC
```

# 7. Event Participants

## 7.1 event_participants

Stores participation of users in events.

### Current Relationship

```text
users 1 — 1 event_participants
events 1 — N event_participants
```

Current schema:

```text
event_participants.user_id = PRIMARY KEY
```

This means a single user can have only **one `event_participants` record in the entire table at a time**.

The schema must be implemented as defined unless the relationship is explicitly changed.

### Fields

| Field        | Type        | Description          |
| ------------ | ----------- | -------------------- |
| `user_id`    | int PK / FK | Participating user   |
| `event_id`   | int FK      | Event                |
| `joined_at`  | timestamp   | Time user joined     |
| `role`       | varchar(20) | Participant role     |
| `status`     | varchar(20) | Participation status |
| `created_at` | timestamp   | Record creation time |
| `updated_at` | timestamp   | Last update time     |

### Capacity Validation

When adding participants, application logic should use:

```text
events.max_participants
```

as the event's participant limit where applicable.

Do not automatically define additional capacity rules unless specified by product requirements.

Stores verification records for users.

### Relationship

```text
users 1 — N user_verifications
```

A user can have multiple verification records.

For example, different verification types or historical verification attempts may exist.

### Fields

| Field               | Type         | Description                  |
| ------------------- | ------------ | ---------------------------- |
| `id`                | int PK       | Verification ID              |
| `user_id`           | int FK       | User                         |
| `verification_type` | varchar(30)  | Verification category        |
| `status`            | varchar(20)  | Verification status          |
| `verified_at`       | timestamp    | Successful verification time |
| `expires_at`        | timestamp    | Verification expiry          |
| `rejected_at`       | timestamp    | Rejection timestamp          |
| `rejection_reason`  | varchar(255) | Reason for rejection         |

# 10. Training Plan

## 10.1 training_plans

Stores training plans connected to events.

A training plan may be manually created or AI suggested.

### Relationships

```text
events 1 — N training_plans

users 1 — N training_plans
       via created_by
```

### Fields

| Field             | Type        | Description                                  |
| ----------------- | ----------- | -------------------------------------------- |
| `id`              | int PK      | Training plan ID                             |
| `created_by`      | int FK      | User who created the plan                    |
| `event_id`        | int FK      | Related event                                |
| `plan_details`    | text        | Training plan details                        |
| `plan_status`     | varchar(20) | Plan status                                  |
| `is_ai_suggested` | boolean     | Whether AI suggested/generated the plan      |
| `scaled_level`    | varchar(20) | Difficulty/fitness level applied to the plan |
| `created_at`      | timestamp   | Record creation time                         |
| `updated_at`      | timestamp   | Last update time                             |

### AI-generated Plans

When the plan is AI-generated or AI-suggested:

```text
is_ai_suggested = true
```

Do not create a separate AI training plan table.

# 14. Implementation Rules for AI Developer

When implementing features against this database:

1. **Use this schema as the source of truth.**
2. Do not invent missing columns.
3. Do not create additional tables unless explicitly requested.
4. Do not rename existing fields for convenience.
5. Do not change relationship cardinality without an explicit requirement.
6. Do not store derived values if they can be calculated from existing data unless explicitly required.
7. Preserve historical records such as `user_history_level` rather than overwriting them.
8. Use foreign keys according to the relationship definitions in this document.
9. Authentication must never store plain-text passwords.
10. Treat fields such as `status`, `role`, `goal_type`, `fitness_level`, `constraint_type`, etc. as domain values whose accepted values must come from product requirements. Do not invent enum values.
11. Nullable fields should remain nullable unless the schema explicitly marks them `[not null]`.
12. Database changes must be reflected back into this `database.md` before being used as a new source of truth.

# 15. Important Current Schema Limitation

The current definition:

```dbml
Table event_participants {
  user_id int [pk]
  event_id int [not null]
}
```

combined with:

```dbml
Ref: users.id - event_participants.user_id
```

means:

```text
One User → Maximum one event_participants row
```

Therefore, under the current schema, a user cannot maintain participation records for multiple events simultaneously or historically.

Do **not** silently change this behavior.

If the intended product behavior is:

```text
One user can join many events
and
one event can contain many users
```

the schema must be explicitly revised to a many-to-many participation model before implementation.
